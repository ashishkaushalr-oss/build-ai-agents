What is a workflow, really?

        
Think about what happens when a supplier invoice arrives at your company. Someone notices it in the inbox, someone types the details into the finance system, someone checks the amount against the purchase order, someone sends a note to the approver. Four small jobs, done in order, by hand, hundreds of times a month. Every automation you will build this week is that chain, drawn as boxes on a canvas. n8n calls the boxes nodes and the chain a workflow.

        
Every workflow begins with a trigger node, which answers the question "when does this run?": when I press Test, when a form is submitted, every weekday at eight, when a request arrives at a webhook. After it come action nodes, each doing exactly one job: set some fields, look something up, send a message, append a row. Data flows along the lines from left to right, and what flows is always the same shape, which Day 4 is about.

        
The habit I want you to leave today with is inspection. Press Test on the left. The run moves one item through the three nodes, and when you click any node you see precisely what came in and what went out. In n8n every node has the same two panels, Input and Output, and nearly every bug you will ever meet is visible in one of them. The field was spelled differently. The number arrived as text. The node ran but produced nothing. Look before you guess.

        
One honest limit of the whiteboard analogy: on a whiteboard the arrow means "then". In n8n the line also carries the data. If a node is not connected, it does not merely run at the wrong time; it has nothing to work on.

        
A workflow is a trigger followed by one-job action nodes, left to right. Read each node's Input and Output before you blame the next one.

One node, many items: n8n loops for you

        
On Monday morning someone in finance opens the overdue report and, row by row, writes a reminder email. Five rows, five emails, the same wording each time. The interesting thing about automating this is that you never say "for each row". Run the workflow on the left and watch: the Google Sheets node returns five items, and the Gmail node, which you configured once, runs five times.

        
Here is the rule underneath. Data between n8n nodes is not one record, it is a list of items, and an action node does its job once for every item it receives. The line between two nodes even tells you how many: "5 items". This is what the syllabus calls the visual execution loop. The loop is real, you just do not draw it. Drag the slider to eight overdue invoices and run again; the Gmail node still has one configuration and sends eight emails.

        
Two consequences matter in practice. First, a node that received zero items usually does nothing at all, and the run looks like it skipped it. If a Gmail node "did not send", check whether anything reached it. Second, sometimes you want the opposite, one action for the whole list: one summary email about all overdue invoices, not five. Every node has a setting called Execute Once that processes only the first item; tick it on the left and see the count fall to one. For a true summary you would merge the items first, which is a Week 8 trick.

        
When a list is huge, hundreds of rows, you do not want hundreds of parallel emails flying out in a burst. The Loop Over Items node feeds them through in batches of a size you choose, with a pause if you like. You will not need it this week, but when you see it in a template you will know why it is there.

        
Data is a list of items. A node runs once per item, automatically. Zero items in means nothing happens; Execute Once means only the first.

Freeze the trigger: data pinning

        
Picture Thursday afternoon. You are building the ticket intake, and every change to the fourth node makes you want to see it run. But the workflow starts from a form submission, so each test means switching tabs, filling in the form, pressing submit, switching back. Ten changes, ten forms. If the trigger were an incoming WhatsApp message or a paid API call, ten tests would mean ten real messages or ten real charges. Builders learn to dread the trigger.

        
Pinning fixes that. Open any node's Output panel after one real run and press the pin icon. From now on, test runs do not execute that node; they replay its saved output, exactly as it was, and everything downstream runs for real against it. Tick the box on the left and run twice: the counter of forms you had to fill in stops moving, and the pinned node shows a pin badge with a dashed outline. Pin what is slow, costly or has a side effect, and keep building.

        
Two rules keep pinning safe. Pinned data is used in manual, in-editor runs only; once the workflow is active, production executions ignore the pin and run the node for real, so you cannot accidentally ship Thursday's test ticket. And unpin before you hand a workflow to a colleague, because a pinned node that silently replays stale data is the most confusing bug in the tool: everything looks fine and nothing is live.

        
A limit worth knowing: pinning stores a snapshot, not a recording. If the form later gains a field, your pinned data will not have it, and the downstream node that needs it will show an empty value. When the shape of the input changes, run it for real once and pin again.

        
Pin a node's output to replay it during test runs instead of re-firing the trigger. Manual runs only; production ignores pins. Unpin before you ship.

What should happen when node three fails at 2 a.m.?

        
Your CRM goes down for maintenance at two in the morning, and at 02:07 a customer submits a ticket. The form posts, the fields are extracted, and the lookup fails. What happens next is not up to luck. It is a setting on the node, and you choose it before anything breaks. Press "Make the CRM fail" on the left and run the three options.

        
Stop Workflow is the default: the run halts, the execution is marked red in the Executions list, and nothing else happens. Simple, and silent; the customer gets no reply and nobody is told until someone looks. Continue passes the failed node's output along as if nothing happened, so the Reply node runs with blank fields and sends "Dear , your order  ". That is worse than stopping. The third option, Continue using error output, gives the node a second, red output that carries the error, and whatever you connect there handles it: a message to you, a row in a "needs a human" sheet, a polite holding reply to the customer.

        
Two more settings live in the same panel. Retry On Fail tries the node again, up to a number of times with a pause, which quietly fixes most "the API was busy for a second" failures. And at the workflow level, Settings has an Error Workflow: a separate workflow that starts with an Error Trigger and runs whenever any production execution fails, receiving the workflow name, the error message and a link to the failed run. Point it at a Slack or email node once, and every workflow you ever activate reports its failures to you.

        
From the MIT course: the tinkering iceberg. In Module 1 of MIT xPRO's Designing and Building AI Products and Services, the fourth stage of the design process is called tinkering, and the instructors warn about a second iceberg. People see the glamorous steps, the specification and the architecture; the time spent finding and fixing bugs and making the thing work in production is an order of magnitude more, roughly ten times. That is why I teach pinning and error handling before the AI Agent node. Next week's agent is the visible tip. Today is the ice underneath.

        
Decide failure before it happens. Default to an error output or an Error Workflow that tells a person; never let Continue send blanks to a customer.

Until now you pressed a button to start a run. Today the website form presses it for you. How does a workflow know a form was submitted?

        
How do you find out that a customer has filled in the contact form on your website? At most companies the honest answer is "someone checks". Support opens the shared inbox every so often, finds three new forms, and starts working. Software can do the same: a Schedule Trigger that wakes up every five minutes and asks the form system "anything new?". That is polling, and it is the top lane on the left. Watch the wait. A ticket submitted a minute after a check sits there until the next one.

        
The other way is to be told. A webhook is a URL that n8n listens on, day and night, and when any system sends an HTTP request to that URL, the workflow starts within a second. The form does not wait to be asked; it calls n8n the moment the customer presses submit. That is the bottom lane, and it is what the syllabus means by an instant trigger. Payments, chat messages, new CRM records, a signed contract: nearly every modern tool can be told "when this happens, call this URL".

        
Polling has two costs you can see in the counter. The wait, which at a fifteen-minute interval averages seven and a half minutes and at worst is the whole interval. And the wasted checks: at one-minute polling a quiet morning means dozens of runs that found nothing, each one using your execution quota. Webhooks run exactly as often as something happens. Try the three intervals and watch both numbers.

        
Where does the webhook story break? The other system has to support it. A modern form builder or payment provider will; a twenty-year-old intranet form or a plain shared mailbox will not, and then polling is the right tool, not a failure. Pick the interval from the business need: an invoice approval can wait fifteen minutes; a chat message cannot.

        
Polling asks on a schedule and pays in waiting and empty checks. A webhook is a URL the other system calls the instant something happens. Use webhooks when the source can call you.

Two URLs and a secret handshake

        
When you add a Webhook node, n8n hands you two addresses that differ by one word. The test URL, with webhook-test in it, works only while you are in the editor and have pressed "Listen for test event" or Test workflow. It accepts one request, shows you the data on the canvas, and stops listening. The production URL, with plain webhook, works only after you switch the workflow to Active, and then it listens around the clock, running silently and logging every run under Executions. Send a request on the left with the wrong combination and you get a 404: nobody is listening at that door.

        
People lose an afternoon to this every week. They test happily, give the form the test URL, close the laptop, and the first real customer gets a 404 at 6 p.m. The rule is short: build with the test URL, ship the production URL, and switch the workflow to Active before you go home.

        
Now the secret handshake. A webhook URL is just a link, and anyone who learns it, a departed contractor, a screenshot in a slide deck, a browser history, can call it and start your workflow with whatever data they like. So we ask the sender to prove itself. In the Webhook node, set Authentication to Header Auth and create a credential: a header name such as X-Ticket-Secret and a long random value. The form must send that exact header with every request. Untick "Send the secret header" on the left and watch the shield bounce the request before any node runs; n8n answers 403 Forbidden and the workflow never starts.

        
One more setting matters for forms: Respond. "Immediately" answers the sender before the workflow runs, "When Last Node Finishes" sends the last node's output, and "Using Respond to Webhook node" lets you decide the status code and body yourself, which is what a form expects and what the lab uses. A webhook that never responds leaves the customer staring at a spinner.

        
webhook-test while you watch, webhook once Active. Always require a secret header, and always respond; a form is waiting on the other end.

Everything that moves between nodes is JSON, and everything you ever type into a node field to reach it is an expression. Curly braces, dots and square brackets

        
You already read JSON every day without knowing it. A row in a spreadsheet is a set of named values: the column "customer" holds "Maya Iyer". A list of attachments on an email is an ordered list. JSON is just the written form of those two shapes. An object is a set of named values inside curly braces: {"name": "Maya Iyer", "plan": "Pro"}. An array is an ordered list inside square brackets: ["safari", "export"]. Objects can hold arrays, arrays can hold objects, and that nesting is the whole language. The ticket on the left uses both.

        
To pull a value out, you write an expression between double curly braces. $json means "the current item", a dot reaches into an object by name, and square brackets reach into an array by position, counting from zero. So {{ $json.customer.email }} is the customer's email and {{ $json.tags[0] }} is the first tag. Zero, not one: the second attachment is attachments[1]. Everyone gets this wrong once; the trainer will tell you kindly.

        
Three more things you will use constantly. .length after an array gives the count. $now is the current date and time, with helpers such as $now.toFormat('yyyyLLdd'). And $('Webhook').item.json reaches back to the output of an earlier node by its name, which saves you from carrying every field forward through every node. Solve the five challenges on the left; they save in this browser.

        
One caution the trainer cannot show you: types. A form sends everything as text, so "12" with quotes is not the number 12, and "12" + 1 gives "121". When a comparison in an IF node behaves strangely, the first suspect is a number that is really a string.

        
Objects are named values, arrays are ordered lists counted from zero. Dots reach into objects, brackets into arrays, and $json is the item in front of you.

Reshaping one system's data for the next

        
The website form calls its fields email, prod, cat and msg, because a web developer named them in 2019. Your Tickets sheet has columns called customer_email, product, category and issue, because that is what the support team understands. Somebody has to translate, and in n8n that somebody is the Edit Fields node, which older templates still call Set. The syllabus calls the job schema transformation: a schema is simply the list of field names and types a system expects.

        
The node is a list of mappings. On the left, the name the next node wants. On the right, an expression over the input, or a fixed value such as normal for priority. Try it: change prod to product in an expression and watch the output report that the field does not exist, then fix it. This is the moment most bugs are born and the moment they are easiest to catch, because both sides are visible at once.

        
Now tick "Include Other Input Fields". The output grows to include everything that came in: the headers, the empty query, and your secret header, which would now be written into the Tickets sheet for anyone with the link to read. Leave that switch off unless you have a reason, and let the Edit Fields node be a deliberate narrowing: only the clean fields continue.

        
In the lab you will add two fields that the form never sent, received_at from $now and a ticket_id built from the timestamp. That is the other half of transformation: not just renaming what arrived, but adding what the next system needs.

        
Edit Fields translates one schema into another: new names on the left, expressions on the right. Keep "Include Other Input Fields" off so only clean fields flow on.

    Where the passwords live, and why you never type them into a node
    
        
    Your ticket intake talks to four outside systems: the form proves itself with a header, Google Sheets needs a Google login, Gmail needs another, Slack needs a token. At work the lazy version of this is a password pasted into a field, screenshotted into a how-to document and emailed to the new hire. n8n makes the right version easier than the wrong one. Every node that needs access asks for a credential, and a credential is a named entry in n8n's vault: stored encrypted, created once, picked from a dropdown by every node that needs it.
    
        
    Click the nodes on the left. The vault card shows what n8n keeps: a name you chose, the type, the secret itself, and which workflows use it. The export underneath shows what the node keeps: an id and a name, nothing more. Download a workflow to share it with a colleague and the secret is not in the file; they import it and pick their own credential of the same type. Rotate a token and you change it in one place; every node follows.
    
        
    Who can use a credential is a separate question from who can see the workflow. n8n lets you share a credential with specific people or a project, so the finance team's Google account can be used by the intake workflow without anyone else being able to open it. For this course, use test accounts you created for the purpose, never your main login, and never put a real customer in a test sheet.
    
        
    The one place the vault cannot protect you is an expression you write yourself. If you paste a token into an HTTP Request header field as plain text instead of choosing a Header Auth credential, it is now in the workflow JSON and in every execution log. The counter on the left stays at zero for a reason.
    
        
    Credentials live encrypted in the vault and are referenced by name. Exported workflows carry only the reference. Never type a secret into a node field.

    One input, several roads: the Switch node
    
        
    In every support team the first job on a new ticket is triage: billing questions to the people who can see invoices, technical faults to an engineer, account changes to whoever can edit accounts. Done by hand, it is a person reading a dropdown and forwarding an email. Done in n8n, it is a Switch node. An IF node has two outputs, true and false. A Switch has as many as you give it, one per rule, and the item leaves by the first output whose rule matches.
    
        
    In Rules mode each rule compares a field to a value: category is equal to billing, category is equal to technical, and so on. You can rename the outputs so the canvas reads like the org chart. Route the tickets on the left one at a time and watch the counters. Then look at the two that do not fit: a ticket whose category is "Other", and one typed in capitals as "BILLING".
    
        
    Those two are the whole lesson. Without a fallback output, an item that matches no rule simply vanishes, with no error and no red node; untick Fallback output and watch the lost counter climb. In the real node, Options has a Fallback Output setting: give the strays an extra output and connect it to a human. And the rules compare text exactly unless you turn on Ignore Case, so "BILLING" is not "billing" until you do. Most routing bugs I have seen were one of these two.
    
        
    Where the Switch stops: it reads a field, it does not read meaning. A customer who picks "Other" and writes "you charged my card twice" is a billing ticket that the Switch cannot recognise. That is exactly the gap the AI Agent node fills next week, when a model such as claude-sonnet-5-5 (model names change; check the current list) reads the issue text and sets the category itself. This week, the fallback output catches what the rules miss.
    
        
    Switch routes an item out of the first matching rule. Always give it a fallback output wired to a person, and turn on Ignore Case when the value is typed by humans.

    Think it through
    
      
    
        
    What is the difference between the test webhook URL and the production one?
    The test URL, with webhook-test in the path, listens only while the editor is open and you have pressed "Listen for test event" or Test workflow; it takes one request, shows the data on the canvas and stops. The production URL, with plain webhook, listens all the time once the workflow is Active, runs silently and logs every run under Executions. Build with the first, give real systems the second, and remember that a workflow you forgot to activate answers 404 to every customer.
    
        
    Write the JSON for a customer record with two phone numbers. Then write the expression that reads the second number.
    Two values of the same kind belong in an array, and each phone needs a type, so an array of objects: {"name": "Priya Nair", "phones": [{"type": "mobile", "number": "+91 98100 11223"}, {"type": "office", "number": "+91 20 2567 8899"}]}. The second number is {{ $json.phones[1].number }}: arrays count from zero, so [1] is the second item, and the dot then reaches into that object for its number.
    
        
    Why should the IF node's false branch respond with a 400 error instead of simply stopping?
    The website form is waiting for an answer. If the workflow stops without responding, the form times out, and the person never learns that their ticket was rejected or why. A 400 with a clear message lets the form show "customer_email, product and issue are required", so they fix the email and resend. Silence also leaves you with no record of how many bad tickets arrived; a 400 is logged in Executions like any other run.
    
        
    You pinned the Webhook node while building. The workflow is now Active. What happens to real tickets?
    Nothing bad, as long as you understand what pinning is. Pinned data is used only in manual, in-editor runs; production executions ignore the pin and run the node for real, so live tickets flow through normally. The risk runs the other way: a colleague opens the editor months later, tests, sees Thursday's old ticket replay and concludes the form is broken. Unpin before you hand a workflow over, and say so in the notes.
